# 41 — Jarvis KURAMA-Parity Pass: Build & QA Summary

This document records what was built for the "clone the KURAMA experience" request and the results of the live QA pass that followed. Confirmed with the user up front: **keep the "Jarvis" branding** — this was a behavior/UX upgrade against the floating companion already built (docs/39, docs/40), not a rename or a rebuild. `AIProvider`, `MockICEEngine`, and the Context Engine (docs/34, 35, 38) are reused exactly as-is; no real AI provider was introduced.

## 1. What Was Built

Exploration confirmed most of the requested experience already existed (persistent mount, floating button → panel → minimize/restore, text + voice, thinking states, confirm-before-save) and that response tone was already warm/confident (verified by reading all of `mockAssistantEngine.ts`). Three real gaps were closed:

- **Simulated streaming** (`src/features/assistant/hooks/useJarvisConversation.ts`) — `pushAssistantMessage` now reveals replies progressively (~2 characters/~16ms) instead of appending the finished string, respecting `prefers-reduced-motion`. A new `isStreaming` flag disables the input alongside `isThinking`. TTS speaks the complete text immediately, in parallel with the visual reveal, not word-by-word.
- **Full-screen conversation mode** — `useJarvisStore` gained `isFullscreen`/`toggleFullscreen()` (reset to `false` on minimize, so reopening always starts docked); `JarvisPanel` gained a header Maximize2/Minimize2 toggle that switches the panel's container between its docked sizing and a full-viewport takeover.
- **Context awareness** — a new `useJarvisPageContext(label, summary)` hook (`src/features/assistant/hooks/useJarvisPageContext.ts`) registers what entity a detail page is showing into `useJarvisStore.activeContext`, clearing on unmount. Wired into the three existing entity-detail pages (`GoalDetail.tsx`, `ProjectDetail.tsx`, `GroceryListDetail.tsx` — confirmed the only ones that exist; every other pillar shows detail inline via dialogs on a list page, no single "current entity" to hang context off). `useJarvisConversation.sendMessage` checks for an anaphoric question against `activeContext` **before** running extraction, answering directly from the tracked summary when both are present.

Drive-by fix: `docs/34_AI_Architecture.md` §1's `AIProvider.converse()` snippet was stale (`Promise<AssistantResponse>`); corrected to match the actually-shipped `Promise<string>`.

## 2. Issues Found and Fixed (all during live QA)

| # | Issue | Where | Fix |
|---|---|---|---|
| 1 | **The context-aware check ran *after* `mockICEEngine.extract()`**, so an anaphoric question ("tell me more about this") never reached it — `extract()`'s `looksLikeQuery()` only recognizes "wh-" questions or a trailing "?", so this fell through to the catch-all `taskRule` and got silently captured as a task titled "Tell me more about this." | `useJarvisConversation.ts` | Reordered: the context-aware check now runs first, before extraction — logically correct anyway (an anaphoric question with active context is unambiguous, there's nothing for extraction to resolve), and avoids touching the shared `extractionRules.ts` classifier. |
| 2 | **`ANAPHORA_PATTERN` (`/\b(this\|that\|it)\b/`) matched the pronoun anywhere in the message**, including inside unrelated phrasing — "What bills are due **this** week?" on a Goal detail page got wrongly hijacked into a goal-summary answer instead of the actual bills answer. Worse than under-triggering: a confidently wrong answer, not just a generic one. | `useJarvisConversation.ts` | Tightened to require the pronoun to follow "about/regarding/on", or to end the message — matches genuine anaphora ("tell me more about this", "what's this?") without matching incidental uses elsewhere in a sentence. Re-verified both directions live: the anaphoric question still gets the entity-specific answer, the unrelated "this week" question no longer does. |
| 3 | **Full-screen mode's `transition-all duration-moderate` got stuck mid-transition** in this test harness — same non-compositing-pane cause docs/40 §3 found for Framer Motion mount tweens, now confirmed to affect plain CSS transitions on already-mounted elements too, not just mount tweens. `getBoundingClientRect()` kept reporting the old docked size (420×640) well after the transition should have finished. | `JarvisPanel.tsx` | Dropped the transition entirely — full-screen toggle is now an instant class swap. Re-verified: correctly resizes to the full viewport (1269.6×800 at 1280×800) and back, and the minimize-resets-fullscreen behavior holds. |

## 3. QA Process

Live-QA'd against the running dev server via the Browser pane, instrumenting `speechSynthesis.speak` and sampling message DOM content at ~50ms intervals to observe the reveal in progress (confirmed steady growth — 6 characters per 50ms sample, matching the 2-char/16ms tick rate exactly — preceded by the existing mock "thinking" delay). Full-screen toggle verified by direct `getBoundingClientRect()` comparison against `window.innerWidth/innerHeight` at desktop width, plus the exit/minimize/reopen cycle. Context awareness verified on all three wired detail pages (including both "this" and "it" phrasing), verified it clears after a client-side navigation away (not just full reload), and verified an unrelated question on the same page is untouched. Regression-checked the capture-confirm-save flow (task count 15→16) and conversation persistence across minimize + navigation (already covered in docs/40, re-touched here only incidentally during the full-screen test sequence).

`tsc -b`, `eslint`, `prettier --check`, and `vite build` were run clean after the initial build and again after each of the three fixes above.

## 4. Remaining Limitations (not fixed — flagged, not silently shipped)

- **Context awareness is wired to 3 of the app's detail pages** (Goal, Project, Grocery List) — the only ones that exist as dedicated routes today. Every other pillar shows entity detail inline (dialogs/sheets on a list page), which has no single "current entity" concept to register — not a gap in this pass, a structural fact about the app's current routing.
- **The anaphora pattern is intentionally conservative** — a contextual-but-not-explicitly-anaphoric question ("what's the progress?" on a Goal page) still falls through to the generic single-domain matcher rather than the specific goal. Named in the original plan as an accepted scope limit; issue #2 above made it *more* conservative, not less, which is the safer direction.
- **Streaming is simulated, not real token delivery** — this system has no real model to stream from; the already-resolved mock reply is revealed progressively instead. This is the same "accepted mock-phase interpretation" pattern already used elsewhere in this project (e.g. docs/39's Context Engine collapsing retrieval+computation+phrasing into one function) — a real provider (Phase 5) would replace this with genuine token streaming behind the same UI.
- **This test harness cannot render CSS transitions/animations reliably** when its Browser pane isn't actively displayed (confirmed twice now — docs/40's Framer Motion mount tweens, and this pass's CSS `transition-all`). Any future animated UI in this project should budget time to verify it live rather than assume a "safer" animation approach (CSS vs. JS) sidesteps the issue — it does not.

## 5. Status

Streaming, full-screen mode, and page-context awareness are built and live-QA'd against the mock providers, with all issues found during QA fixed and re-verified, not just fixed-and-assumed-working. Jarvis's architecture (interaction layer / ICE / Context Engine / domain modules) is unchanged in kind from docs/39–40. Real-provider integration remains Phase 5.
