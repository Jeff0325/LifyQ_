# 40 — Jarvis as the Center of LifyQ: Build & QA Summary

This document records what was built for the "Jarvis as the Center of LifyQ" UX change (docs/39's floating-companion addendum) and the results of the live QA pass that followed. This is a UI/interaction-layer change only — `AIProvider`/`MockICEEngine`/the Context Engine (docs/34, 35, 38) are reused exactly as Phase 3.5 built them (docs/39), unchanged in kind. No real AI provider was introduced.

## 1. What Was Built

- **`useJarvisStore`** (`src/stores/useJarvisStore.ts`) — a new persisted Zustand store (same `persist` pattern as `useOnboardingStore`) owning `panelState` (`'chathead' | 'intro' | 'expanded' | 'listening'`) and a `pendingQuery` handoff queue. Only `hasSeenIntro` is persisted (`partialize`) — `panelState` resets to `'chathead'` on every fresh load, matching the rest of the app's mock-session model.
- **`useSpeechSynthesis`** (`src/features/assistant/hooks/useSpeechSynthesis.ts`) — a genuinely functional wrapper around the browser's `speechSynthesis` API, mirroring `useSpeechRecognition`'s shape (`{isSupported, isSpeaking, speak, stop, error}`). `speak()` cancels any in-flight utterance first, so a fast back-and-forth conversation doesn't queue stale audio.
- **`useJarvisConversation`** (`src/features/assistant/hooks/useJarvisConversation.ts`) — the single unified conversation hook, replacing the earlier split where `useCapture` (extraction) and `useAssistantChat` (chat) were two separate, page-scoped instances. One `sendMessage()` call tries extraction first (confirm-before-save unchanged), falls through to the Context Engine → `converse()` on a query, and speaks every assistant reply — confirmed product decision: **every** reply is spoken, typed or voice-originated alike, not just voice-mode ones.
- **Floating UI** (`src/features/assistant/components/`) — `JarvisRoot` (mounted once in `RootLayout`, sibling of `<Outlet/>`, owns the single `useJarvisConversation()` instance for the app's lifetime), `JarvisChatHead` (minimized bubble), `JarvisIntro` (one-time first-launch animation with the exact specified greeting), `JarvisPanel` (expanded conversation, reusing `ChatThread`/`CaptureConfirmSheet` unchanged), `JarvisListening` (dedicated Voice Mode takeover with a pulse animation), `JarvisRedirect` (deep-link safety net for the old routes).
- **Nav integration** — `assistant` removed from `PRIMARY_NAV_ITEMS`/`MOBILE_TAB_ITEM_IDS`; `BottomNav` gained a dedicated, elevated, brand-gradient center Jarvis button (`[Home][Tasks][•Jarvis•][Goals][More]`); `Sidebar` gained an equivalent brand-gradient row above the routed list; `TopBar`'s existing "Ask Jarvis" trigger now opens the panel instead of navigating.
- **Routing** — `ROUTES.assistant`/`ROUTES.capture` now render `JarvisRedirect` (queues any `?q=` param, opens the panel, redirects home); `src/pages/Ai.tsx` and `src/pages/Capture.tsx` deleted, superseded.

## 2. QA Process

Live-QA'd against the running dev server via the Browser pane: first-launch intro (exact greeting text, tap-to-continue, `hasSeenIntro` persistence, second-launch skip verified after a real page reload), a query-shaped message (text reply **and** `speechSynthesis.speak()` invocation both confirmed via an instrumented spy), a capture-shaped message (`CaptureConfirmSheet` opened on top of the panel, Save confirmed writing to the domain's repository — task count 14→15 — and closing back to just the panel), minimize → two client-side navigations → reopen via chat head (conversation history fully intact, proving `JarvisRoot`'s single global instance), the `/assistant?q=...` deep link (redirected home, auto-submitted once the panel reached `'expanded'`, correct Life Records-sourced answer), Voice Mode (mic click correctly triggered a real `SpeechRecognition.start()` — confirmed via the browser's own permission prompt — and gracefully returned to the conversation without sending anything when mic access was unavailable, thanks to `sendMessage`'s empty-transcript guard), and a full nav sweep at both mobile (375px) and desktop (1280px) widths confirming the exact `[Home][Tasks][•Jarvis•][Goals][More]` bottom-nav layout and the Sidebar's dedicated Jarvis row.

`tsc -b`, `eslint`, `prettier --check`, and `vite build` were run clean after the build and again after the fix below.

## 3. Issues Found and Fixed

| # | Issue | Where | Fix |
|---|---|---|---|
| 1 | **`react-hooks/refs` lint violation** — `useJarvisConversation` originally mirrored `messages` into a `useRef` and mutated `.current` during render (to avoid `sendMessage` depending on `messages`), which this project's lint config forbids (refs must not be written during render). | `useJarvisConversation.ts` | Removed the ref entirely; `sendMessage`'s `useCallback` now simply depends on `messages` directly, matching the exact pattern `useAssistantChat.send` already used before this change. |
| 2 | **`motion.button`/`motion.div` `initial`→`animate` entrance tweens got permanently stuck at their `initial` value** (`transform: scale(0)`, invisible and unclickable) on `JarvisChatHead` — found live-testing the very first click on the floating bubble, which silently missed (zero-sized element) and fell through to whatever was underneath. Root cause isolated to this specific test harness: the Browser pane reported "not compositing frames" when not actively displayed, which appears to stall Framer Motion's (and even a plain CSS `animate-in` retry's) mount tweens indefinitely rather than settling once compositing resumes. | `JarvisChatHead.tsx` | Simplified to a plain static button with only `active:scale-95` (pure CSS, no animation library) for press feedback — correctness matters more than a decorative pop-in for a bubble that's on-screen for the entire session. `JarvisIntro`'s and `JarvisListening`'s animations were left as designed (Framer Motion, matching this codebase's established custom-animation precedent) since they're genuinely premium, intentional moments and the DOM/functional correctness underneath them was independently verified via direct DOM/state inspection, not pixel geometry. |
| 3 | **Chat head bubble grazed the bottom nav by ~1.5px** at mobile width once its position was fixed (issue #2's rewrite dropped the transform that had coincidentally been hiding this). | `JarvisChatHead.tsx` | Bumped the offset from `4.5rem` to `5.25rem`; re-verified clear at 375px width. |

## 4. Remaining Limitations (not fixed — flagged, not silently shipped)

- **Voice Mode could not be exercised end-to-end** — the sandboxed QA browser blocks microphone access, so only the request-and-graceful-fallback path was verified live, not an actual recognized transcript flowing through to a saved capture or a spoken reply. The code path is unchanged from Stage 1's already-functional `useSpeechRecognition` (docs/39 §4's same flagged gap), now additionally wrapped in `JarvisListening`'s UI.
- **`useAssistantChat.ts` and `useCapture.ts` are superseded but not deleted** — still exported from `src/features/assistant/index.ts`, no longer the primary UI path (nothing renders `<Ai/>`/`<Capture/>` anymore). Left in place on purpose, same precedent as `DailyOverview.tsx` in the Stage 2 build (docs/39 §4) — a still-valid isolated primitive, not dead weight worth a churn-only deletion pass.
- **Main JS bundle grew from ~528 kB to ~636 kB (gzipped 170 kB→189 kB)** — expected and unavoidable in kind: `JarvisRoot` and everything it renders must be in the always-loaded main chunk (mounted in `RootLayout`, present on every route), unlike route-level code splitting. Flagged consistently with the same pre-existing bundle-size note in docs/30 §8/docs/31 §5/docs/39 §4.
- **The exact universal fallback phrase** ("I don't have that information in your LifyQ yet...") was not retrofitted across every existing `converseMock`/Context Engine rule's own empty-state phrasing — this was explicitly scoped out of this UX-focused change (docs/39-addendum plan §7) as a separate content-consistency pass, not silently dropped.

## 5. Status

The floating-companion pattern (persistent chat head, one-time intro, unified type-or-speak panel, dedicated Listening Mode, and a distinctive center bottom-nav button) is built and live-QA'd against the mock providers, per the architecture-preservation constraint in the approved plan — Jarvis/ICE/Context Engine/existing-modules layering is exactly as Phase 3.5 left it (docs/39). Real-provider integration remains Phase 5, unaffected by this change.
