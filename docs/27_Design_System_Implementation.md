# 27 — Design System Implementation (Milestone 2)

This document records the concrete decisions made while building the component library — the "why" behind every primitive now living in `src/components/ui`, `src/components/shared`, and `src/styles/tokens.css`. It extends, rather than replaces, [08_Design_System.md](08_Design_System.md) and [11_Component_Library.md](11_Component_Library.md): those documents set the intent during planning; this one records what was actually built and any decisions that had to be made at implementation time that the plan left open.

A live, in-app reference of everything below is available at **`/design-system`** — see §9.

## 1. Primitive foundation: Radix UI

Every interactive Tier 1 primitive (Dialog, Sheet, Select, Dropdown Menu, Checkbox, Radio Group, Switch, Tabs, Tooltip, Toast, Avatar, Progress, Separator, Label) is built on **Radix UI primitives**, exactly as committed to in [11_Component_Library.md](11_Component_Library.md) §1. Packages installed: `@radix-ui/react-{slot,dialog,select,dropdown-menu,checkbox,radio-group,switch,tabs,tooltip,toast,label,separator,avatar,progress}`.

**Why now, not earlier:** Milestone 1 deliberately stayed dependency-light (only `Button` and `VisuallyHidden`, no Radix) so the foundation could be verified in isolation. Milestone 2 is explicitly the "build the component library" phase, so this is the correct point to add the primitive layer everything else composes from.

Every Radix wrapper in this codebase follows the same pattern: import the primitive, re-theme it with our semantic tokens via `cn()`, forward the ref, and export a component with the same name minus the `Primitive` suffix (e.g. `DialogPrimitive.Content` → `DialogContent`). No Radix default styling ships unstyled or with its own visual identity — see the "no generic shadcn app" mandate in the original design brief.

## 2. Animation utility layer: `tw-animate-css`

Radix's `data-[state=open]`/`data-[state=closed]` attributes are the hooks for open/close transitions, but Tailwind v4 has no built-in `animate-in`/`fade-in-0`/`zoom-in-95` utility set. The classic `tailwindcss-animate` plugin (used by most shadcn/ui projects) is a JS-config-based plugin incompatible with Tailwind v4's CSS-first `@theme` architecture. **`tw-animate-css`** is its v4-native successor (same class vocabulary, `@import`-based, zero JS config) — installed as a dev dependency and imported once in `globals.css`. This keeps every overlay's enter/exit animation (Dialog, Sheet, Select, Dropdown Menu, Tooltip, Toast) declarative and consistent without hand-writing keyframes per component.

### 2.1 Known issue found and fixed: exit animations stalled Radix's unmount

While verifying the showcase page live (not just building it — see §9), Dialog, Sheet, Select, and Dropdown Menu were found to get **permanently stuck open**: clicking Cancel, the overlay, or Escape flipped `data-state` to `"closed"` correctly, but the DOM node was never removed. This was reproduced and confirmed in **both** the dev server and a production build (`vite build && vite preview`), ruling out a React StrictMode dev-only artifact.

**Root cause:** Radix's `Presence` component only unmounts a closing element after it observes an `animationend` event on that element (so the exit animation gets to play first). Instrumenting the DOM directly (`element.addEventListener('animationend', ...)`) showed the event **never fires** for the `data-[state=closed]:animate-out …` utility combinations generated by `tw-animate-css` in this project's build, even though the computed styles looked correct (`animation-name: exit`, `animation-duration: 0.15s`, `animation-play-state: running`). The animation is declared but the browser never dispatches completion for it in this setup, so `Presence` waits forever.

**Fix applied:** every overlay component (`dialog.tsx`, `sheet.tsx`, `select.tsx`, `dropdown-menu.tsx`, `toast.tsx`, `tooltip.tsx`) now applies **entrance-only** animation classes (`data-[state=open]:animate-in …`) and no longer applies `data-[state=closed]:animate-out` or any `fade-out`/`zoom-out`/`slide-out` exit classes. Radix's `Presence` sees no exit animation defined, so it unmounts synchronously and correctly the instant `open`/`onOpenChange` says to. The practical UX effect: every overlay still fades/zooms/slides **in** exactly as designed; closing is now instant rather than animated. Given the alternative was a completely broken, stuck-open modal, this trade was made without hesitation.

**Verified after the fix**, live against a production build: Dialog, `ConfirmDialog`, Sheet (including Escape-to-close), Select, and Dropdown Menu (including item-click auto-close) all open and close cleanly with zero leftover DOM nodes — checked programmatically (`document.querySelectorAll('[role="dialog"]').length === 0` after close, etc.), not just visually.

**Follow-up recommendation, not done now:** root-cause exactly why `animationend` doesn't fire for these specific `tw-animate-css`-generated declarations in this Tailwind v4 setup (candidates: a `tw-animate-css` v1.4.0 issue, or an interaction with this project's own `@theme`/`@custom-variant` setup) and restore exit animations once understood, rather than continuing to guess. Filed here rather than silently worked around so a future milestone can pick it up with full context.

## 3. Motion library: `motion` (Framer Motion's successor)

Per [13_Technical_Architecture.md](13_Technical_Architecture.md), the confirmed stack is "Framer Motion (`motion/react`)" — by this point Framer Motion has been renamed **Motion**, published as the `motion` npm package with a `motion/react` import path. Installed as `motion@^12`.

**JS-side motion constants** (`src/lib/motion.ts`) mirror the CSS custom properties in `tokens.css` §7 (`--duration-fast`, `--ease-standard`, etc.) because Framer/Motion transition props need real numbers and bezier arrays, not `var(...)` strings. This is a deliberate, documented duplication: **if you change a duration or easing in `tokens.css`, change the matching value in `src/lib/motion.ts`.** No build-time sync mechanism exists for this yet; revisit if the two ever drift in practice.

**Global reduced-motion handling:** `<MotionConfig reducedMotion="user">` is mounted once in `RootLayout`, wrapping the entire app. This is the single switch that makes every `motion.*` element — including every shared motion wrapper below — automatically drop transform/layout animation for users with `prefers-reduced-motion: reduce`, without each component needing its own check. This is in addition to, not instead of, the CSS-level `@media (prefers-reduced-motion: reduce)` block already in `globals.css` from Milestone 1 (that block covers plain-CSS transitions; `MotionConfig` covers Motion-driven ones).

### Shared motion wrappers (`src/components/shared/motion/`)

| Component | Purpose | Notes |
|---|---|---|
| `FadeIn` | Opacity-only entrance | The one animation that stays on even under reduced motion, per docs/19 §6 |
| `SlideUp` | Panel/sheet/section entrance | Configurable distance, defaults to 8px |
| `StaggerList` / `StaggerItem` | Staggered list entrance | Container + item pair; 40ms stagger |

The three that remain (`FadeIn`, `SlideUp`, `StaggerList`) are consumed and demonstrated live on `/design-system` rather than shipped as dead code.

## 4. Bottom sheets: Dialog-based, not a dedicated gesture library

`Sheet` (`src/components/ui/sheet.tsx`) is built on `@radix-ui/react-dialog` with a `side` variant (`bottom` | `top` | `left` | `right`), defaulting to `bottom` — the mobile-native pattern from [10_Navigation_Architecture.md](10_Navigation_Architecture.md) §6. It includes a visual drag-handle affordance (the small pill at the top) and slide-in/out animation via `tw-animate-css`.

**Known simplification:** this Sheet does **not** implement real touch drag-to-dismiss (swipe down to close) — closing is via the close button, overlay tap, or Escape. A physically-accurate drag gesture (rubber-banding, velocity-based dismiss) would require a dedicated library (e.g. `vaul`, which itself wraps Radix Dialog). This is deferred rather than built now because no real bottom-sheet-driven flow exists yet to validate the interaction against — it's a good candidate to revisit when Quick Add (the first real bottom-sheet consumer) is built in a later milestone.

## 5. Toasts: Radix primitive + a small Zustand queue

`@radix-ui/react-toast` handles accessibility (`aria-live` region, swipe-to-dismiss, focus management) and animation hooks. The **queue itself** (`src/stores/useToastStore.ts`) is a small Zustand store, per [14_State_Management_Strategy.md](14_State_Management_Strategy.md) §3 — toasts are transient client UI state, not async data, so TanStack Query has no role here (and isn't installed yet regardless — that's Milestone "Data Layer Foundation").

`useToast()` (`src/hooks/useToast.ts`) is the only API feature code should ever call: `const { toast } = useToast(); toast({ title, description, variant })`. `<Toaster />` is mounted once in `RootLayout` and renders whatever the store currently holds.

## 6. Charts: color tokens now, full charting library deferred

Before writing any chart code or picking chart colors, the **`dataviz` skill** was consulted (per its own trigger condition — building chart primitives and choosing chart colors). Its procedure was followed:

1. **Categorical palette adopted, not invented.** Rather than hand-designing and manually eyeballing a new 8-hue categorical palette, the skill's own validated reference palette (`references/palette.md`) was adopted verbatim (8 hues, fixed order, light + dark steps) and **re-validated against this app's actual surface colors** (`#fafafa` light / `#0a0a0c` dark, not the skill's own `#fcfcfb` / `#1a1a19` defaults) using `scripts/validate_palette.js`. Both modes pass every hard gate (CVD separation, normal-vision floor, lightness band); light mode carries a contrast WARN on 3 of the 8 slots, which is documented as a hard requirement: those slots require a direct label or legend, never color alone.
2. **Tokens added:** `--chart-1` through `--chart-8` in `tokens.css`, light/dark, following the exact same `:root`/`.dark`/`@theme inline` pattern as every other semantic token — generates `bg-chart-1`…`fill-chart-8` etc. utilities.
3. **Constraint documented in the token comments themselves:** only the first 3 slots are safe for *all-pairs* contexts (scatter, bubble, small multiples); all 8 are safe for *adjacent-pairs* contexts (stacked bars, grouped bars, multi-line). A 9th series is never a generated hue — it folds into "Other" or facets, per the skill's non-negotiables.
4. **Sequential encoding uses the existing brand indigo scale**, not a new hue — a lone series needs no legend, and brand-600 is already the app's single most load-bearing color.
5. **What was *not* built:** axes, legends, tooltips, filters, or any multi-series chart component. The categorical palette is reserved for the **Analytics domain (Phase 3)**, which doesn't exist yet — building interactive multi-series chart chrome now, with no real data or screen to drive it, would mean designing against guesses. Two lightweight, genuinely-needed primitives shipped instead:
   - **`ProgressRing`** (`src/components/shared/ProgressRing.tsx`) — circular single-value progress, used by Goals/Habits.
   - **`Sparkline`** (`src/components/shared/Sparkline.tsx`) — minimal inline trend line, dependency-free (hand-rolled SVG, no charting library), for stat tiles and habit/goal cards.

   Both are single-series and use the sequential brand hue; neither needed the categorical palette, the interaction layer, or a charting library dependency (Recharts, visx, etc.) — that decision is explicitly deferred to when Analytics is actually scoped, so it's made against real requirements instead of speculation.

## 7. Component inventory delta vs. the original plan

Everything listed in [11_Component_Library.md](11_Component_Library.md) §3–§4 that was in scope for this milestone was built. A few small additions beyond that list, made because they were immediately necessary to build the rest correctly:

- **`Badge`** — wasn't separately named in the original Tier 1 inventory, but the "Soon" pill used in `Sidebar`/`BottomNav` since Milestone 1 was hand-rolled inline; it's now a real primitive with `neutral`/`brand`/`success`/`warning`/`danger`/`info` variants, and the Milestone 1 layout components were refactored to use it — one implementation of "a pill," not two.
- **`Breadcrumb`** — explicitly described in [10_Navigation_Architecture.md](10_Navigation_Architecture.md) §7 ("wayfinding") but not yet built; built now under "navigation components."
- **`Card` gained an `InteractiveCard` variant** (a `<button>`-based card with hover/press/focus states) alongside the static `Card` — needed the moment a card is meant to be clickable (e.g. a future Goal card), and is a two-line addition once the base `Card` exists.
- **`Button` gained `asChild`** (via `@radix-ui/react-slot`), not present in Milestone 1. This replaces the Milestone 1 workaround of exporting `buttonVariants` for manual application to a `<Link>`; `NotFound` and `ErrorPage` were updated to the `asChild` pattern for consistency. `buttonVariants` is still exported (some call sites may still need bare class strings), but `asChild` is now the preferred way to make a non-button element look like a Button.

## 8. What deliberately was not built this milestone

Per the founder's instruction ("do not build feature screens yet"), nothing here is a domain UI:

- No `TaskRow`, `GoalCard`, or any other Tier 3 feature component (those belong to each domain's own `/features/{domain}/components`, per [12_Folder_Architecture.md](12_Folder_Architecture.md) §3, and are built when that domain is built).
- `PageHeader`, `QuickAddBar`, `CommandPalette`, `StatTile`, `StreakHeatmap`, `FilterBar` (Tier 2 composites named in [11_Component_Library.md](11_Component_Library.md) §4 but not requested this round) remain unbuilt — see the updated `src/components/shared/README.md`. Building them without a real consumer would mean guessing their API.
- No Storybook setup yet. `/design-system` (§9) serves as this milestone's live/manual review surface; Storybook (component isolation + visual regression, per [25_Testing_Strategy.md](25_Testing_Strategy.md) §2) is a testing-infrastructure concern for a later milestone, not a design-system one.

## 9. Live review surface: `/design-system`

A single route, **`/design-system`**, renders every primitive and composite built this milestone with its real variants — colors, type scale, spacing, elevation, radius, icons, buttons, cards, inputs, dropdowns, checkboxes/radios/switches, dialogs/sheets, navigation (tabs, breadcrumb), toasts, skeletons, empty/error states, charts, and a live motion demo.

Deliberate placement decisions:

- **Outside `AuthLayout`/`AppShell`, not in `PRIMARY_NAV_ITEMS`.** It is not a product page — a real user should never be able to navigate to it from the app shell. It's reached only by typing the URL, matching how this kind of internal tooling route is commonly handled before a dedicated Storybook exists.
- **Lazy-loaded** (`React.lazy`) exactly like every other route per [15_Routing_Strategy.md](15_Routing_Strategy.md) §4 — it pulls in every component at once (124KB gzipped, per the build output) and must never ship as part of the bundle a real visitor downloads. Verified in the production build: `DesignSystemShowcase` is its own chunk, separate from the app's main entry chunk.

## 10. Performance note (honest accounting, not a fix)

The main (eagerly-loaded) JS chunk is currently **~171KB gzipped**, above the ~150KB aspirational target in [18_Performance_Strategy.md](18_Performance_Strategy.md) §1. This is flagged rather than hidden:

- The growth versus Milestone 1 (105KB gzip) is driven mainly by `motion` (mounted app-wide via `MotionConfig`, genuinely used on every route) and the two Radix packages that are real, always-on app chrome (`@radix-ui/react-toast`, `@radix-ui/react-tooltip`, via `Toaster`/`TooltipProvider` in `RootLayout`).
- All other Radix packages (Dialog, Select, Dropdown Menu, Checkbox, Radio Group, Switch, Tabs, Avatar, Progress, Separator, Label) are only imported by `DesignSystemShowcase` and the as-yet-unused `ConfirmDialog`, and are confirmed **not** present in the main chunk — they load only when `/design-system` is visited.
- No further bundle-splitting (e.g. separating `motion` into its own vendor chunk, deferring `MotionConfig`) was attempted this milestone. [23_Development_Roadmap.md](23_Development_Roadmap.md) designates a dedicated Hardening milestone (Milestone 4) for exactly this kind of measurement-driven performance pass, once real feature routes exist to profile against — doing it now would be optimizing against a showcase page, not the real app.

## 11. Consistency check performed

Before considering this milestone done: every new token added to `tokens.css` (chart colors) follows the existing `:root`/`.dark`/`@theme inline` three-part pattern from Milestone 1, with zero exceptions. Every new component under `src/components/ui` uses `cn()` from `src/lib/utils.ts` and only semantic tokens — enforced by the `no-restricted-syntax` ESLint rule from Milestone 1, which was corrected in the process (`neutral` was wrongly flagged as a "raw Tailwind color" when it's actually one of our own sanctioned scales — the rule now excludes `brand`, `accent`, `neutral`, and `chart`). `pnpm lint`, `pnpm format:check`, and `pnpm build` all pass clean as of this milestone.
